# 账号系统与 PostgreSQL 改造设计

状态：设计稿，尚未实现或部署。日期：2026-10-18。

## 1. 目标与范围

将当前单用户 LiftLab 改为可以安全承载多个用户的 App。保留对话主页面；首次登录后创建个人画像，每位用户独立保存饮食、计划、RM、聊天、训练、媒体与教练设置。

本期推荐：邮箱验证 + 密码登录、PostgreSQL、可撤销的设备会话。手机号验证码和微信登录作为后续登录方式，共用同一个用户体系。

当前仅形成设计，不安装数据库、不迁移现有记录、不开放公网接口。

## 2. 当前代码中需要改造的地方

- `backend/app.py` 使用 sqlite3，`records(id, kind, payload)` 未记录数据归属；普通记录全部共享。
- `backend/coach.py` 使用 `local-profile`、`local-coach-profile` 等固定标识，聊天历史也没有用户过滤。
- `backend/reminders.py` 使用 `local-coach-reminders`；教练和提醒设置需要分用户。
- `backend/workouts.py` 的训练记录查询、回顾、修订号需要分用户。
- `backend/library.py` 食物和动作库允许写入，需要将系统库的管理权限与普通用户使用权限分开。
- `mobile/lib/app.dart` 的 JSON 请求与 multipart 上传各自发起请求，均需接入同一个鉴权客户端。
- 现有 SQLite 专用备份脚本不能直接用于 PostgreSQL，需要增加 PostgreSQL 备份和恢复流程。

不能通过更换数据库连接地址完成此次改造；SQL、数据模型、用户归属和业务调用链均需调整。

## 3. 用户端流程

### 3.1 注册与首次使用

1. App 启动后展示登录页面，提供登录、创建账号、找回密码。
2. 用户阅读隐私政策与用户协议，注册时记录所同意的版本和时间。
3. 输入邮箱和密码，发送验证邮件；验证码验证通过后在事务中创建用户。
4. 注册验证通过后直接建立登录会话，进入首次画像采集。
5. 完成年龄、身高、体重、目标、经验、限制与训练时间设置，也允许跳过后通过对话补充。
6. 后端缺少关键画像时，AI 明确提示补充，不能从其他用户或旧单用户记录填充。

未登录期间不调用收费 AI 接口。登录后保留现有“对话首页 + 侧边栏”交互。

### 3.2 日常登录与自动登录

- 已验证邮箱 + 密码登录；凭据错误统一提示，不区分账号不存在或密码错误。
- Access Token 有效期建议 15 分钟；Refresh Token 绝对有效期 30 天、连续闲置上限 7 天，均可配置。
- App 重启时通过安全存储中的 Refresh Token 恢复会话；失败则回到登录页。
- Access Token 只保存在内存，Refresh Token 保存于平台安全存储，不使用普通 SharedPreferences 存放令牌。
- 过期时只允许一个刷新请求执行，其他请求等待结果，避免多请求同时轮换刷新令牌。
- 401 不直接重放可能产生费用或写入的请求；确认是认证阶段返回的令牌过期错误后才重试一次，写入与 AI 请求使用用户范围内的幂等键。

### 3.3 账号管理

“我”增加：账号信息、修改密码、登录设备、退出当前设备、退出全部设备、数据导出和账号注销。

- 修改密码需重新验证当前密码；找回密码需验证邮件挑战，成功后撤销全部旧会话。
- 更换邮箱需重新认证，并验证新邮箱；向原邮箱发送变更通知。
- 注销需近期重新认证；立即阻止新请求并撤销会话，异步清除个人记录和媒体。对话或上传中的在途结果不得重新写回已注销账号。
- 账号注销和个人数据清除的时间、备份保留与到期清除方式在隐私政策中明确；不承诺立刻从全部备份中物理抹除。
- 切换账号或退出时清除本地个人缓存，并取消该用户的本地训练/饮食通知；重新登录后按当前用户设置重建。

## 4. 后端认证与授权

### 4.1 技术选择

| 内容 | 方案 |
|---|---|
| API | 保留 FastAPI / Pydantic |
| 密码 | pwdlib + Argon2id；只存哈希，参数根据服务器资源压测 |
| Access Token | PyJWT，固定允许的签名算法，校验签名、签发方、接收方、过期时间 |
| Refresh Token | 密码学安全随机值；数据库只存摘要；每次使用后轮换 |
| 数据层 | SQLAlchemy 2.x + psycopg 3 |
| 数据库版本管理 | Alembic |
| Flutter | 统一 ApiClient / AuthRepository + 平台安全存储 |
| HTTPS | Caddy 代理至本机 FastAPI |

JWT 仅携带用户 ID、会话 ID、签发及过期时间等鉴权字段，不包含画像、伤病、聊天内容或模型密钥。签名 JWT 不等同于加密数据。

每个受保护请求同时验证 JWT、会话是否有效、用户是否有效。因此退出、改密和停用可以立即阻止旧令牌继续访问；初期每次检查 PostgreSQL，不额外依赖 Redis。

会话记录包含用户、设备展示名称、创建/最近使用时间、绝对到期、空闲到期和撤销时间。设备名称仅用于展示，不作为认证凭据。

刷新令牌轮换使用数据库事务和行锁：同一旧令牌只能成功一次。保留已使用令牌摘要至会话到期；检测已用令牌再次使用时撤销该会话并要求重新登录。客户端串行刷新；刷新成功但响应丢失导致重登录是本期可接受的体验取舍。

### 4.2 权限边界

- 匿名：最小健康检查、注册、登录、验证和恢复流程。公开响应不暴露模型配置与个人数据。
- 普通用户：只操作自己的个人资料和业务记录；读取系统食物库、动作库。
- 管理员：维护系统库和账号状态；不能通过注册参数或客户端修改获得管理员身份。
- 管理员默认不提供读取用户聊天和健康画像的通用入口；需要此类能力时另行设计授权与审计。

资源查询统一使用 `id + current_user.id`。请求体里的 `user_id` 不能决定数据归属。访问其他用户的资源返回 404，避免暴露资源是否存在。

SQLAlchemy 仓储层显式接收 user_id；路由、AI 上下文组装、后台任务和幂等记录均传递该身份。不用进程级全局变量保存当前用户。复合外键或等价约束确保计划项、训练项、媒体分析等关联对象属于同一个用户。

PostgreSQL 行级安全可作为后续第二层防护；应用层所有权检查本期必须具备。若启用行级安全，需专用非绕过角色和事务内用户上下文，验证连接池复用不会残留身份。

### 4.3 登录与费用保护

- 无多因素认证的密码策略建议 15–128 个字符，允许空格和 Unicode，不要求机械拼凑大小写/特殊符号；限制请求大小并检查常见弱密码。
- 登录按 IP 和账号标识共同限流，渐进退避，不采用可被他人反复触发的永久锁号。
- 验证码建议 10 分钟到期、单次使用、最多 5 次验证；发送至少间隔 60 秒，并设置每账号/IP/日额度。具体阈值上线前配置。
- 短验证码用服务端密钥参与 HMAC 后存储，不能对低熵验证码仅做普通无密钥哈希。验证码验证和消费使用事务。
- 邮件发送、注册和找回密码统一使用不泄露账号存在性的响应。邮件进入持久任务队列并有限重试，不在日志中记录验证码。
- 内测默认使用邀请注册；公开注册前配置邮件服务、发送域名认证和滥用控制，不能以“开发验证码”替代真实验证。
- AI 接口按用户限制并发、请求频率和每日预算；收费请求先占用额度，完成后结算，使用 `(user_id, action, idempotency_key)` 唯一约束防重复计费。
- 上传需身份验证、用户归属、文件类型/体积验证；私有文件通过鉴权接口读取或短期签名链接访问，不能整体挂到公开静态目录。
- 日志记录事件与请求 ID，去除密码、令牌、验证码、邮件正文和完整健康/聊天内容。

## 5. 接口设计

所有路径以下为建议的新接口，现有业务路径可先保留并增加鉴权。

| 方法与路径 | 用途 |
|---|---|
| POST /api/auth/register | 创建注册挑战并发送验证邮件 |
| POST /api/auth/register/verify | 消费验证码、创建账号和会话 |
| POST /api/auth/login | 密码登录并创建会话 |
| POST /api/auth/refresh | 轮换刷新令牌，签发新令牌 |
| POST /api/auth/logout | 撤销当前会话 |
| POST /api/auth/logout-all | 撤销全部会话 |
| POST /api/auth/password/forgot | 发出重置挑战，统一响应 |
| POST /api/auth/password/reset | 消费重置挑战、更新密码、撤销旧会话 |
| POST /api/auth/password/change | 验证当前密码后修改密码并撤销旧会话 |
| GET /api/auth/sessions | 当前用户的设备会话列表 |
| DELETE /api/auth/sessions/{session_id} | 撤销自己的指定会话 |
| GET /api/me | 当前账号信息，不返回密码哈希 |
| POST /api/me/email/change | 重新认证后创建新邮箱验证挑战 |
| POST /api/me/email/verify | 消费挑战并更新邮箱绑定 |
| POST /api/me/export | 创建本人数据导出任务 |
| DELETE /api/me | 重新认证后注销账号并创建清除任务 |

注册/登录/刷新/验证码接口设置 Cache-Control: no-store。401 表示未认证或会话失效，403 表示已认证但无功能权限，429 表示限流。错误体使用稳定业务码，客户端不要依靠匹配自然语言错误。

原生 App 使用 Bearer 请求头；如发布浏览器版本，优先使用 Secure/HttpOnly Cookie 管理刷新凭据并增加 CSRF 防护，不将 Refresh Token 放入 localStorage。浏览器 CORS 配置允许明确来源和所需请求头；CORS 不能替代认证。

## 6. 数据库选择与结构

### 6.1 推荐 PostgreSQL

SQLite 仍适合单用户本地原型；PostgreSQL 和 MySQL 都能承载本 App 的常规账号、饮食和训练业务。推荐 PostgreSQL 的项目原因是：画像事实、模型结构化输出和动作分析结果包含变化较多的 JSON，JSONB 支持查询与索引，适合与强关系约束结合。

不把所有数据重新塞进一张 JSON 表。可查询/约束的账号、归属、日期、营养和训练负荷使用明确字段；模型原始结果、证据和版本快照使用 JSONB。仅给实际检索的 JSON 路径建索引。

| 表组 | 建议核心表 | 关键约束或字段 |
|---|---|---|
| 账号 | users, auth_identities, password_credentials | UUID 主键；用户状态；角色；身份提供方及规范化标识唯一；密码哈希与更新时间 |
| 会话 | auth_sessions, refresh_tokens | user_id、会话到期/撤销；令牌摘要唯一、使用时间及继任关系 |
| 验证与事件 | auth_challenges, auth_events, consent_records | 用途、有效期、尝试次数、消费时间；最小审计信息；协议版本 |
| 画像 | profiles, profile_facts | 一人一份基础画像；事实的来源聊天/训练 ID、时间、状态、模型/规则版本 |
| 对话 | conversations, messages | user_id、会话 ID、角色、内容、创建时间；禁止跨用户拼接上下文 |
| 计划/RM | training_plans, plan_items, rm_records | user_id、动作引用、组次/重量/休息、RM 测量日；生成快照与版本 |
| 饮食 | meal_entries | user_id、当地日期/时区、餐次、克数；记录当时营养快照，避免库更新改写历史 |
| 训练 | workout_sessions, workout_sets, workout_reviews | user_id、计划引用、动作/负荷/次数/RPE/疼痛反馈；回顾及画像来源 |
| 设置 | coach_settings, reminder_settings | user_id 唯一；教练人设、时区、训练时间、饮食提醒 |
| 文件 | media_files, media_analyses | user_id、私有存储键、类型、大小、状态；分析结果 JSONB 和模型版本 |
| 系统库 | foods, exercises | 系统只读数据；动作关节分类、部位、注意事项、示例资源、版本 |
| 任务与额度 | jobs, ai_usage, idempotency_requests | 用户归属、状态、重试/到期、请求唯一性与预算占用/结算 |

邮箱地址按产品约定规范化，保留原始展示值；不移除加号别名、不对所有提供商统一删除点号。账号与登录身份解耦，为后续手机号/微信绑定保留扩展空间。

所有私人表以 user_id 关联账号；常用索引包含 `(user_id, created_at)`、`(user_id, day)`、`(user_id, exercise_id, measured_on)`。账号身份唯一约束、事务和外键由数据库保证，不只依赖先查后写。

时间戳统一用 timestamptz 存储绝对时刻，用户时区单独记录；饮食“当天”按用户时区计算。重量与营养使用有明确精度的 numeric。

### 6.2 部署方式

初期可将 PostgreSQL 部署在现有服务器，仅监听回环地址，数据库端口不对公网开放。应用使用最小权限账号，迁移使用单独角色；密码放服务器环境配置，App 不直接连接数据库。

安装版本选择官方仍维护且与部署环境匹配的主版本，锁定依赖并制定更新方式；本设计不要求追最新主版本。安装前先检查服务器 CPU、内存、磁盘和连接数预算，不承诺未知配置可承载的用户规模。

同机部署节约额外实例费用，也与后端共享资源和故障风险。正式运营时可迁移至同地域、内网连接的华为云托管 PostgreSQL；是否立即购买依据实际容量、预算和恢复要求决定。

初期使用 `pg_dump` + 私有异地备份，并进行恢复演练；每日一次备份可能丢失最多约一天的数据。需要更低数据丢失窗口时配置 WAL 持续归档和时间点恢复或购买对应托管能力。数据库备份之外同时保存用户媒体及其清单，演练配套恢复。

## 7. 实施和切换顺序

1. 建立 SQLAlchemy 数据层和 Alembic 迁移，创建账号、会话、系统库和业务表。
2. 在隔离测试库完成认证和用户归属改造，调整 coach、workouts、reminders 和 AI 上下文。
3. 接入邮件服务、验证挑战、限流、任务和日志脱敏。内测保持邀请注册。
4. Flutter 增加登录/注册/恢复、会话恢复、安全存储和账号管理，统一 JSON/上传鉴权并清理用户缓存与提醒。
5. 在服务器安装 PostgreSQL 并验证空库初始化、食物/动作种子与数据库备份恢复。
6. 切换前检查云端当前记录，做一致性备份并记录切换点。此前用户选择空白个人档案，不自动迁移电脑个人记录，也不把匿名记录绑定给首个注册者；发现新云端记录时先明确归属。
7. 短暂停止写入，迁移批准保留的数据、校验数量/关联/样本，再切换 DATABASE_URL。验证后恢复服务。
8. 配置域名、HTTPS 和受保护入口，构建手机新版，用移动网络验收。

旧 SQLite 仅作为有访问限制的回退快照保留。新系统恢复写入后，不能直接切回旧 SQLite 并假定数据完整；回退需要处理切换后的新增记录。数据库结构迁移也不能只回滚代码。

## 8. 验收条件

- 两个测试用户的画像、聊天、AI 上下文、计划、饮食、训练、媒体和提醒完全独立；枚举其他用户 ID 不能读写或引用其资源。
- 普通用户不能修改系统食物/动作库或提升角色；私有文件无匿名直链。
- 重复注册、验证码并发消费、刷新并发、过期/复用令牌、改密/退出/停用后的旧令牌均有实际测试。
- 手机重启可恢复有效会话；刷新失效回到登录；账号切换不显示旧聊天、不触发旧提醒。
- AI 请求幂等按用户隔离；跨用户/失败重试不会混用缓存或重复扣费。
- 注销后后台 AI/上传任务不能重建已清除的数据；验证恢复、备份到期和媒体清除流程。
- 必须使用真实 PostgreSQL 跑隔离/事务/约束测试，不能仅用 SQLite 代替验证。
- 备份可在独立数据库和媒体目录恢复；手机断开电脑后，经 HTTPS 可完成登录、聊天、饮食、训练和上传。

## 9. 外部配置清单

- 最终域名、DNS 与 HTTPS 入口。
- 验证邮件服务及发信域名配置；当前未配置。后续若启用短信，另外需要供应商、签名/模板及发送额度。
- 数据库连接、JWT 签名密钥、验证码 HMAC 密钥：服务器生成并保管，不放 APK、不提交 Git。
- 正式隐私政策/用户协议、数据保存和注销策略；测试方案不替代公开运营所需手续。
- PostgreSQL 和媒体的私有异地备份位置、保留策略及告警。
